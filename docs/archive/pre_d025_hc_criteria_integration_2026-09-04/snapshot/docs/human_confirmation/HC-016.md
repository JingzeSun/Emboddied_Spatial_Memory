# HC-016：证据达到什么条件才允许提交修订

## 为什么必须由人确认

“观测与旧图不一致”不等于“旧事实已经错误”。遮挡、视野外、位姿漂移、身份误配和传感器异常都会制造表面冲突。若提交门槛过低，系统会频繁破坏正确记忆；门槛过高，又会长期保留过期事实。

该选择决定哪些结果可进入正式图、哪些只能进入隔离区，也决定 precision/recall 的权衡，因此需要显式的人类确认。

## 需要确认的问题

证据满足什么条件时，系统可以执行 `INVALIDATE / RELINK / SUPERSEDE` 等破坏性修订？

### 选项 A：按操作类型设置结构化前置条件（建议）

- `RELINK`：身份关联通过，并有新位置正证据；若同时使旧位置失效，还要求旧位置在可靠可见条件下被否定，或有可验证动作证据。
- `INVALIDATE`：目标区域可见、位姿与传感器质量合格，且负证据达到约定强度。
- `SUPERSEDE`：新旧状态互斥、身份一致、时间顺序合法，且新状态有正证据。
- 任一关键条件不满足时，不改正式事实，输出 `QUARANTINE` 或 `PRESERVE`。

### 选项 B：统一置信度阈值

- 所有修订只比较一个总置信度。
- 易实现，但会把身份、可见性、位姿和传感器质量混成不可解释的分数。

### 选项 C：固定连续帧数

- 连续若干帧一致才提交。
- 对静态视角简单，但相邻帧高度相关，不能自然处理遮挡、重新观察和单次高质量证据。

## 建议的判定字段

```yaml
commit_gate:
  identity_ok: null
  visibility_ok: null
  pose_ok: null
  sensor_ok: null
  temporal_order_ok: null
  positive_evidence_ok: null
  negative_evidence_ok: null
  evidence_groups: []
  decision: preserve | quarantine | commit
  failed_preconditions: []
```

其中 `evidence_groups` 用来标记证据独立性；同一视角的相邻帧默认属于同一组，不能简单按帧数重复计票。

## 若采用选项 A，实验如何判定

- 每类破坏性操作分别报告 commit precision、commit recall 与 abstention/coverage，不能只报一个平均准确率。
- 遮挡、视野外、位姿冲突、身份不确定时发生正式失效，均列为硬失败。
- 在可靠可见且证据充分的样例中长期拒绝更新，计为漏修订，而不是“更保守所以正确”。
- 具体数值阈值只可在验证集调节；测试集仅运行一次冻结配置。

## 数字算例：每个提交 criterion 是什么

假设正式测试前的 validation 有 50 个“应该提交”和 20 个“应该 preserve/quarantine”的案例：

- `commit precision`：系统提交 35 次，其中 32 次整笔事务合法，`32/35=91.4%`；衡量“改了的有多少该改”；
- `commit recall`：应提交 50 次，正确提交 32 次，`32/50=64%`；衡量“该改的完成多少”；
- `abstention/coverage`：70 例中系统对 35 例提交，coverage=`35/70=50%`；保守不是自动更好；
- `unsafe commit rate`：20 个应拒绝案例误提交 1 个，`1/20=5%`；若它是遮挡导致删除，仍触发硬失败；
- `atomic validity`：40 个事务有 1 个只撤销旧位置却未写入约定的新状态，`39/40=97.5%`，且该次为硬失败；
- `evidence-group count`：同一相机扫视的连续 10 帧只算 1 组；换视点后另 6 帧为第 2 组，不是 16 票。

“单次高质量观测”需要结构化条件，例如 identity=0.98、预期可见 coverage=0.99、无可信遮挡且 pose/
sensor 均过门；这些数字只是计算例，不是冻结阈值。若任一关键字段失败，输出应是 `QUARANTINE`
或 `PRESERVE`，而不是把多个低质量分数平均成通过。
