# HC-015：未知变化时刻的有效时间语义

## 为什么必须由人确认

在部分可观测环境里，智能体通常只知道：对象在上一次可靠观测时仍位于旧位置，在本次可靠观测时已经不在旧位置或出现在新位置。真实移动时刻发生在两次观测之间，不能把“第一次看见变化的时间”冒充为真实事件时间。

这一选择会直接决定时序场景图的字段、标注规范、查询语义和时间指标，因此不能由实现代码自行决定。

## 需要确认的问题

当真实变化时刻未知时，正式事实版本采用哪一种有效时间表达？

### 选项 A：区间删失（建议）

- 旧事实记录 `last_supported_at` 与 `first_contradicted_at`。
- 新事实记录 `first_supported_at`；若有可验证的动作或外部事件时间，再补 `event_time`。
- 只声明真实变化发生在 `(last_supported_at, first_contradicted_at]` 内，不伪造精确时间点。
- `observed_at` 与 `recorded_at` 始终单独保存。

### 选项 B：首次观测时间近似事件时间

- 用 `first_contradicted_at` 或 `first_supported_at` 作为变化时刻。
- 实现简单，但会把感知延迟写入世界状态，且难以诚实评价时间误差。

### 选项 C：区间中点近似

- 用最后支持与首次矛盾观测之间的中点作为估计时刻，同时保存区间。
- 可输出单点估计，但必须明确这是估计值，不能作为 ground truth。

## 建议的最小字段

```yaml
validity:
  last_supported_at: null
  first_contradicted_at: null
  first_supported_at: null
  event_time: null
  event_time_source: null
observed_at: null
recorded_at: null
```

## 若采用选项 A，实验如何判定

- 真实事件时间已知的仿真样例：检查区间是否覆盖真实事件；另报区间宽度。
- 真实事件时间未知的真实样例：只检查区间顺序、非重叠约束和证据可追溯性，不计算虚假的点时间误差。
- 若系统输出精确 `event_time`，必须有对应的 `event_time_source`，否则为硬失败。

## 数字算例：每个时间 criterion 是什么

假设杯子在 `t=10.0 s` 最后一次确认仍在桌上，在 `t=14.0 s` 第一次可靠确认已经不在，仿真日志
显示真实移动发生于 `t=12.0 s`，系统于 `t=14.3 s` 写入版本：

- `valid-time coverage`：输出 `(10.0, 14.0]` 覆盖 12.0，记 1；输出 `(13.0, 14.0]` 不覆盖，记 0；
- `interval width`：`14.0-10.0=4.0 s`，越窄信息越多，但不能靠漏掉真值来换窄区间；
- `observation-time error`：只有允许点估计且有真值时才算。若估计 12.8，绝对误差为 0.8 s；
- `transaction-time validity`：`recorded_at=14.3 >= observed_at=14.0` 合法；若写成 13.8 则非法；
- `provenance completeness`：60 个新/失效事实有 57 个包含 evidence ID、时间和规则版本，为 95%；
  但若规则要求每次写入都可追溯，这仍触发硬失败。

在 3RScan 这类没有真实移动时刻的数据上，只能评区间顺序、宽度与来源完整性；不得计算一个伪造的
点误差。在 AI2-THOR scripted action 有事件日志时，才可计算 coverage 和可选的点估计误差。
